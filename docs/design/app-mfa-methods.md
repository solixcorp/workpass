# Application MFA methods

Application policies store `mfaMethods` as a comma-separated set. Supported IDs are `totp`, `hotp`, `duo`, `passkey`, `email`, and `sms`. An empty list retains the existing rule: any session-bound MFA proof suffices. The migration gives existing policies an empty list and existing proof rows an `unknown` method. Unknown proofs satisfy only an empty list. A non-empty list is retained but inactive while `requireMfa` is false. Observe-mode policies may save globally unavailable methods.

Admin GET/PUT `/api/admin/app-access-policies` use `mfaMethods` arrays. GET also supplies `availableMfaMethods` with Korean labels and global availability. Email and SMS share the global OTP switch; SMS also requires an SMS provider and email requires transactional email availability. Passkey availability follows the global passkey switch and the WorkPass sign-in policy. In enforce mode, a required method that is unavailable globally is rejected on save.

Proofs contain an accumulating set of methods scoped to a session token and user. OTP send records an HMAC of the code, its channel and send time; a successful verification uses the matching unexpired channel (three minutes, the configured Better Auth default). Neither OTP nor its plaintext is stored in the channel table. Missing or ambiguous channel metadata yields `unknown`. Backup codes also remain `unknown`.

`passkey` means the session has a user-verifying passkey proof, either from sign-in or from the in-session step-up endpoints. The latter issue a five-minute, single-use challenge bound to the session and user, restrict credentials to that user, and verify the assertion with the same SimpleWebAuthn library as the Better Auth plugin, including origin, RP ID, user verification and counter. An app-only passkey proof does not satisfy risk-based step-up: passkey sign-in itself may be the event being assessed, and passkey proof recording does not mark risk challenges satisfied. Other second-factor proofs retain the existing challenge satisfaction behavior.

An app-specific challenge can be requested with `GET /api/security/step-up/challenge?subject=<encoded-policy-subject>`. It returns `requiredMethods`, usable `methods` and UI on a 403, or a Korean denial with `requiredMethods` when no method can be offered. OTP currently routes to a verified phone first, otherwise email, so an account with a verified phone is not offered email until channel selection is implemented. The UI maps `email`/`sms` to the existing `otp` control, `duo` to `duo_push`, and passkeys to `passkey`; backup codes are not offered for specific app methods. The client must implement the passkey UI and call the step-up endpoints.

Successful TOTP verification records `totp`, verified HOTP codes record `hotp`, and Duo push approvals record `duo`. Successful passkey sign-in records `passkey` when its session can be resolved and the proof write succeeds; verified OTP codes record `email` or `sms` when the matching channel is available.
