# Per-application outbound SCIM

An administrator can configure one outbound SCIM target per application at `/api/admin/applications/{slug}/provisioning`. Its journal and mappings use `app:{slug}`; the existing environment-configured deployment target is independent. The bearer token is sealed at rest using `AEAD_SEALING_KEY` and associated data `provisioning:{slug}`. API responses never include it. Removing an application deletes its target configuration but retains journal entries and mappings.

URLs must be HTTPS, cannot contain credentials, query strings or fragments, and reject loopback/private IPv4 literals, local names, and IPv6 literals. This validation does not resolve DNS or prevent DNS rebinding: deployments must enforce outbound network restrictions to prevent access to private addresses. SCIM reads and mutations do not follow redirects.

The test action reads `ServiceProviderConfig` with an eight-second timeout. Sync scans at most 50 local users per call, ordered by ID. The persisted cursor advances until `remaining` reaches zero, then a later call starts a new full scan. `processed` counts scanned users (including unassigned users), not just mutations. A user is provisioned only if not banned and the existing portal visibility check allows the application. Mapped users who fail that check are deactivated; eligible mapped users are updated and reactivated, and eligible unmapped users are created. Failures, including users blocked by existing open operations, are counted and revisited on a later full scan. Changes occurring behind the cursor are picked up in a subsequent scan.

All mutations go through the existing SCIM executor and operation journal. Pending, in-progress and outcome-unknown operations continue to block another operation for the same target and user; uncertain outcomes require manual reconciliation. The sync lock prevents concurrent scans of one application; a worker terminated before its `finally` block may leave it locked, requiring operator database intervention after checking the journal. This is intentional fail-closed behavior, not an automatic retry mechanism.

Sync is administrator-triggered; there is no automatic push on assignment changes, scheduler for application targets, group provisioning, remote reconciliation, or downstream deletion. The current portal visibility check also excludes dashboard-hidden and disabled applications. Deactivation retains the mapping so a later sync can reactivate the same remote user. Operators should reconcile old mappings before repointing a target or recreating a deleted application with the same slug.
