# SAML IdP foundation

The application migration creates a service-provider registration table. An authenticated administrator can create a disabled registration through `POST /api/admin/saml-service-providers` with `entityId`, `acsUrl` and PEM `signingCertificate`, list registrations with `GET /api/admin/saml-service-providers`, and retrieve one using `GET /api/admin/saml-service-providers/{id}`. The POST requires the exact configured browser origin and is audited. Registrations are always disabled; there is no endpoint to enable one, accept an AuthnRequest, sign a response, or issue an assertion. The `enabled` field alone does not enable any SAML flow. PEM input is structurally checked, not cryptographically validated as an X.509 certificate.

Samlify documents IdP response generation and signed request validation, but it is a Node.js library and requires an XML schema validator. Workers support for the complete dependency tree and validator has not been demonstrated. Do not skip schema validation, invent XML signature verification, or deploy a partially implemented SAML login path. A Workers-compatible library and validator, signing-key lifecycle, replay protection, request/ACS validation, authorization policy, and signed-response interoperability with a real test service provider remain required.

The application migration also creates a D1 request-claim table. `claimVerifiedSamlRequest` provides a bounded, atomic one-time claim scoped to an SP, but is deliberately not exposed as an endpoint: callers must first verify the request signature, issuer, destination, and freshness. It does not yet establish a complete replay-protected login flow. Expired claims are removed when a new claim is attempted and by the daily scheduled cleanup.

The backend also includes a standalone HTTP-Redirect binding signature verifier for RSA-SHA256 using a caller-supplied trusted public key. It rejects duplicate binding parameters and verifies the original URL-encoded bytes.

## Verification chain (not enabled yet)

The following pieces now exist and are covered by Bun-native primitive tests (`tests/saml-verification.test.ts`, run with `bun test`), which simulate an SP sending a signed redirect request and perform a full signed-response round trip:

- `src/saml/certificates.ts` extracts the RSA SubjectPublicKeyInfo from the registered PEM certificate with bounded DER walking and imports it as a non-extractable WebCrypto verify key. It requires RSA of at least 2048 bits. It does not validate the certificate chain, expiry or revocation; trusting a certificate is an administrator decision made at registration time.
- `src/saml/request-binding.ts` inflates the verified SAMLRequest with a hard output bound (raw DEFLATE or zlib framing) and parses an allowlisted AuthnRequest shape: fixed namespaces, fixed element order, no DOCTYPE, comments, processing instructions, character references, unknown attributes or unknown children. Semantic checks (version, ID shape, timestamp window, Destination equals the configured IdP SSO endpoint, ACS equality, POST binding) run in the route.
- `src/saml/assertion.ts` builds and signs a Response with an enveloped RSA-SHA256 signature over the Assertion. The XML is produced canonically by construction (sorted attribute order, namespaces declared where visibly used, context-correct entity escaping) so the digest the service provider recomputes matches the builders' bytes; the tests verify both the signature over SignedInfo and the digest over the assertion with the enveloped transform applied.
- `src/saml/protocol-routes.ts` wires `GET /saml/sso` as a sequential gate: IdP signing material configured (otherwise 503), provider registered and enabled, binding signature verified against the certificate-derived key, verified bytes reparsed and revalidated, one-time claim via `claimVerifiedSamlRequest` before any use, and only then a signed response issued to an authenticated user and delivered through an auto-submitting POST form to the registered ACS.

Nothing is wired to a live login yet: every registration is still created disabled and there is no enable endpoint, no IdP signing key provisioning flow, no login-session handoff page to authenticate users mid-flow, and no attribute/NameID policy beyond the account email. `InResponseTo` replay claiming, signature verification and identity issuance must never be separated: the route is the only caller pattern approved. Signed-response interoperability with a real test service provider (`Verify SAML interoperability`) remains required before any provider may be enabled.

## Enablement, metadata and sign-in handoff

- `POST /api/admin/saml-service-providers/{id}/enable` flips a registration to enabled. It requires an administrator session from the exact configured origin and is audited; it also imports the stored certificate into a usable RSA verify key first and refuses with 400 if the certificate is not usable. `POST /api/admin/saml-service-providers/{id}/disable` is symmetric and always allowed.
- `GET /saml/metadata` publishes the unsigned identity provider metadata document (entity ID, signing KeyDescriptor with `WantAuthnRequestsSigned="true"`, emailAddress NameID format, and Redirect plus POST SingleSignOnService endpoints at the configured SSO URL). It returns 503 until IdP signing material is configured. Publishing requires no credentials; the metadata contains only public material.
- `bun run scripts/generate-saml-key.ts` generates the IdP signing key pair and a self-signed X.509 certificate for the three `SAML_IDP_*` configuration values, and self-checks the produced material by importing the certificate as the runtime would and verifying probe signatures from both the exported and re-imported private key. Options: `--cn <name>`, `--days <n>` (default three years), `--out <dir>` (writes PEMs, refuses to overwrite an existing key), `--bits <n>` (2048–4096, default 2048), `--entity <https url>`. The private key must be stored as a secret, never committed; the certificate is self-signed and its lifecycle (issuance, rotation with overlap, revocation) remains an open requirement.
- On a fully verified but unauthenticated SSO request the route renders a minimal sign-in page instead of failing. The page keeps the original request query in the address bar and reloads the same URL after a successful better-auth sign-in, so signature verification, full revalidation and the one-time claim all run again on the authenticated round. No redirect parameter exists, so the handoff cannot be forged into a redirect elsewhere. The page supports email/username plus password sign-in via the existing `/api/auth/sign-in/*` endpoints with the configured rate limits; passkey sign-in from this page is not implemented yet.
- Every SSO stage remains non-skippable and the claim still happens before any assertion is built. Live interop with a test service provider remains the gate before using SAML sign-in for real users.
