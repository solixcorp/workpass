# SAML IdP implementation status

The backend contains an experimental SP-initiated login flow at `GET /saml/sso` and public metadata at `GET /saml/metadata`. Administrators can register an SP, initially disabled, and explicitly enable or disable it. Enablement verifies that the stored SP certificate contains a usable RSA key. Admin mutations require an administrator session and the configured origin and are audited.

The SSO endpoint accepts signed HTTP-Redirect AuthnRequests with RSA-SHA256. It selects the enabled SP from the request issuer, checks the signature against its registered certificate, validates a restricted XML request shape and its freshness, destination and ACS, and atomically claims the request ID before issuing a signed assertion to the registered ACS. Unsupported ForceAuthn requests are rejected; passive requests without a session cannot trigger a login page. Authenticated sessions use their creation time as the authentication time. Unauthenticated users can sign in on the rendered same-origin page through the existing password endpoints or a passkey ceremony (the latter is written against the standard WebAuthn API and not yet exercised in a real browser), then reload the same signed request. Only HTTP-Redirect requests are advertised; responses use HTTP-POST.

Configure `SAML_IDP_ENTITY_ID`, `SAML_IDP_SIGNING_CERTIFICATE`, and the secret `SAML_IDP_SIGNING_PRIVATE_KEY`. The signing pair is checked for a match before use. `bun run saml:keygen` generates initial material; protect the private key and do not commit it. Key rotation, expiry and revocation procedures are not implemented. SP certificates are explicitly trusted by registration, not chain-validated.

The request parser intentionally accepts only a narrow XML subset, not arbitrary SAML schemas. NameID is the account email. The response signs the assertion rather than the entire response. Real service-provider interoperability, independent XML signature verification, SP authorization policy, and deployment security review remain unverified. Do not use this implementation for production authentication until those checks are completed. The existing tests include expectations predating current protocol restrictions and do not establish interoperability.
