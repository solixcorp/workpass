# Outbound SCIM connector foundation

The project has a server-side SCIM 2.0 transport for creating users, modifying selected user attributes, and deactivating users with `active: false`. It also has a D1 mapping table for local user IDs and target-side user IDs and an operation journal with atomic claims. Administrators may read an entry at `GET /api/admin/scim-operations/{id}` and initiate a single-target operation through `POST /api/admin/scim-operations`. No production target has been selected and no downstream account has been provisioned.

The transport requires an HTTPS base URL and caller-supplied bearer token, disables redirects, does not store credentials, and never automatically retries a mutation. A timeout or server error has an unknown outcome; operators must reconcile the target before retrying, especially for create. Mapping writes refuse to overwrite existing mappings. The create response must include a target user ID; a missing or malformed response after a successful HTTP mutation also needs reconciliation.

The protected application migration creates `scim_user_mappings`. No inbound SCIM server is implied: inbound scope is still undecided. The manually invoked endpoint is disabled by default and uses a single server-configured `SCIM_TARGET_ID`, `SCIM_BASE_URL`, and secret `SCIM_BEARER_TOKEN`; it accepts no remote URL or token from the request. It requires an administrator session, exact configured Origin, and audit recording. It reads name, username and email from the local user record; create uses the immutable local ID as `externalId`. Target-specific schemas, automatic lifecycle integration, retries, cleanup, user-to-app assignment, and production interoperability remain open. Never infer deletion from a missing mapping.

The migration also creates `scim_operations`. At most one pending, in-progress, or outcome-unknown operation may exist per target/user. No automatic lease expiry or retry is performed: an interrupted in-progress operation and an unknown outcome need explicit reconciliation, so a crashed worker cannot silently cause a duplicate downstream create. The journal stores no token or profile payload.
